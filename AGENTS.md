# Open Pantry

A simple pantry companion for seeing what is at home, using food in time, and buying what is missing. TanStack Start (React, TypeScript) with Drizzle on PostgreSQL and Better Auth. Product behaviour is specified in `docs/`: read [data-and-rules.md](docs/data-and-rules.md) before touching quantities, units, dates, matching or shopping, and [auth-and-permissions.md](docs/auth-and-permissions.md) before touching access control.

## Commands

Node 22.18+ and pnpm (the version is pinned in `package.json`).

```bash
pnpm install
pnpm db:up          # local Postgres in Docker
pnpm db:migrate     # apply migrations to the local database
pnpm dev            # http://localhost:3000
pnpm check          # oxfmt --check, oxlint (warnings fail), tsc --noEmit
pnpm test           # Vitest
pnpm build          # production build plus the migration bundle
```

Run `pnpm format`, `pnpm check` and `pnpm test` before committing; CI runs the same checks and the build.

## Stack decisions

- Use the VoidZero tools standalone: Vite, Vitest, Oxlint, Oxfmt. Do not add Vite+, ESLint, Biome or Prettier.
- Keep the TanStack Start setup stock. `vite.config.ts` should stay close to the template. `src/routeTree.gen.ts` is generated; never edit it by hand.
- Styling is plain CSS: design tokens in `src/styles.css` and one CSS Module per component. No Tailwind, shadcn or utility CSS. Interactive behaviour comes from Radix Primitives. See [src/components/README.md](src/components/README.md).

## Code layout

- `src/routes/`: TanStack Router file routes. API handlers live under `src/routes/api/`.
- `src/domains/<name>/`: server and domain logic per area (`auth`, `pantry`, `sharing`, `theme`). Server functions are in `*.functions.ts`.
- `src/components/<Name>/`: `Name.tsx` plus `Name.module.css`.
- `src/db/`: `schema.ts` (ours), `auth-schema.ts` (generated by `pnpm auth:generate`; do not edit by hand), `migrate.ts` (production migration runner).
- Import with the `#/` alias (`#/domains/...`), including the `.ts`/`.tsx` extension.
- Authorization is enforced on the server for every read and mutation, never only in the UI.

## Database changes

Change `src/db/schema.ts`, run `pnpm db:generate`, review the SQL in `drizzle/` and commit it with the code. Do not use `db:push` for anything that will be deployed. Migrations run automatically on the server before the new version starts and are never reversed, so keep each release compatible with the previous one: add columns and tables first, remove them in a later release.

Never edit a migration that is already on `main`. If two pull requests each add a migration, the second to merge must merge `main` in, delete its own migration and run `pnpm db:generate` again: Drizzle only runs a migration whose timestamp is newer than the last applied one, so an older one is skipped silently. CI enforces this (`scripts/check-migrations.ts`): it fails when `schema.ts` and the migrations disagree, when applied migrations were edited or are out of order, when a new migration drops, renames, retypes or deletes things or adds a `NOT NULL` column without `DEFAULT` (mark a deliberate exception with a `-- allow-destructive: <reason>` comment in the SQL file), and when the migrations cannot be applied to an empty database or on top of `main`'s.

## Deployment

`main` is protected: changes land only through a pull request whose `checks` job passes. Merging to `main` publishes `ghcr.io/niklaslimberg/open-pantry` and the home server deploys it within about five minutes (database backup, migrations, health check, automatic restore of the previous image if unhealthy). Treat every merge as a production deploy. Details and recovery steps: [deploy/README.md](deploy/README.md). Changes to files in `deploy/` are not deployed automatically; they need a manual rollout on the server.
